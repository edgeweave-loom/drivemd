# Setting up the iOS Simulator for the device checks

How to prepare a Mac for the iOS part of [`device-checks.md`](device-checks.md): the Simulator's devices, what to install, the tools the agent drives them with, and what to do when one fails. [`device-setup-android.md`](device-setup-android.md) does the same for the Android Emulator.

## Devices

Use the newest iOS runtime that Xcode has (`xcrun simctl list runtimes`) and these devices, from `xcrun simctl list devicetypes`:

| Name                | Device type                                    | Why                                                                                                                                                    |
| ------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `DriveMD iPhone`    | the newest iPhone Pro, with the Dynamic Island | the notch, the home bar, the phone layout upright and sideways (under 500 pt tall, so it keeps the phone layout)                                       |
| `DriveMD iPad`      | an iPad Air 11-inch, 820 × 1180 pt             | upright, between 768 and 1023 pt wide: the navigation rail and the folder's drawer; sideways, 1180 pt: the navigation drawer and the computer's layout |
| `DriveMD iPhone SE` | iPhone SE (3rd generation), optional           | a home button and no notch: no inset should leave an empty band                                                                                        |

Create each one fresh for a run, so that no Home Screen app, `localStorage` or Google session is left from the last one:

1. Run `xcrun simctl list devices` once: after an Xcode update, the first `simctl` command restarts CoreSimulator ("CoreSimulator detected version change").
2. `xcrun simctl delete "DriveMD iPhone"` if it exists, then `xcrun simctl create "DriveMD iPhone" <device type> <runtime>`, and `xcrun simctl boot` it.
3. Open their windows in DeviceHub (see Tools) before opening Safari: DeviceHub, opened before the devices existed, showed none of them, and opening a booted device there restarted it, closing Safari.
4. Give the status bar a fixed time and battery, so that screenshots compare: `xcrun simctl status_bar <device> override --time 9:41 --batteryState charged --batteryLevel 100`.

A device can shut down during the run, for example when its window closes: `xcrun simctl list devices` shows it, and it needs `xcrun simctl boot` and the status bar override again.

## Install

Once per Mac:

- Xcode with an iOS runtime (Xcode ▸ Settings ▸ Components, or `xcodebuild -downloadPlatform iOS`), opened once to accept its license.
- Node.js 24, which the repository also runs on, and pnpm, which starts mobile-mcp, and [uv](https://docs.astral.sh/uv/) for the measuring scripts: `brew install node@24 pnpm uv`, then `brew link node@24`, since Homebrew's `node` is a newer major version.
- [mobile-mcp](https://github.com/mobile-next/mobile-mcp), Claude Code's MCP server for the Simulator, which the repository's `.mcp.json` declares: when Claude Code offers to use it, accept `mobile`, then check with `/mcp` that it is connected. Whoever does not run these checks declines, and nothing is installed. The server brings mobilecli, which drives the Simulator, and drives Android emulators too, through `adb`.

How `.mcp.json` runs it:

- **No telemetry.** It turns mobile-mcp's telemetry off, since it would otherwise send each tool call's name to its developers, and offer a tool that sends them what the agent writes in it.
- **A pinned version.** It pins a version at least a week old, as Dependabot's cooldown does, and Dependabot does not update it: raise it by hand.
- **The repository's rules.** `pnpm dlx`, run from the repository, holds the server's own dependencies to `pnpm-workspace.yaml`'s rules, releases at least a week old among them.
- **Hoisted.** mobile-mcp looks for mobilecli's binary only beside its own package, where pnpm's isolated `node_modules` leaves none, so `.mcp.json` installs it hoisted (`node-linker=hoisted`). pnpm keeps a `dlx` install for a day whatever its options: after changing them, run the command once with `--config.dlx-cache-max-age=0`.

When a `mobile` tool fails, see [Troubleshooting](#troubleshooting).

Before the first check, the agent checks these with `xcodebuild -version`, `xcrun simctl list runtimes`, `node -v`, `pnpm -v`, `uv --version` and whether the `mobile` tools are available, and tells the developer what is missing.

## Tools

- **mobile-mcp** taps (`mobile_click_on_screen_at_coordinates`, `mobile_long_press_on_screen_at_coordinates`), swipes from a point in one of four directions (`mobile_swipe_on_screen`), types (`mobile_type_keys`), lists the screen's elements (`mobile_list_elements_on_screen`), presses Home (`mobile_press_button` with `HOME`, to send the Home Screen app to the background), opens addresses (`mobile_open_url`; on a fresh device, Safari's first one can stay on its start page or loading, while the address typed in the address bar loads), takes screenshots (`mobile_take_screenshot`) and fills the clipboard (`mobile_clipboard`). Tap an element by the reference that the list gives; otherwise, convert a screenshot's pixels with the mapping that comes with it. `mobile_save_screenshot` writes only under the working directory or the temporary one: save the report's screenshots with `xcrun simctl io <device> screenshot <path>` instead, so that none lands in the repository.
- `xcrun simctl` does the rest: the theme (`ui <device> appearance light|dark`), the status bar (`status_bar`) and the screenshots (`io <device> screenshot`).
- **The Simulator's window.** Xcode 27 has no Simulator app: its devices show in DeviceHub (`/Applications/Xcode.app/Contents/Applications/DeviceHub.app`, `open -a` it by that path), one device to a window, picked in the window's sidebar. Its menus act on the device whose window is in front (`name of window 1` says which):
  - **Turning the device:** **Device ▸ Orientation ▸ Portrait / Landscape Left / Landscape Right** (Xcode 27.1) or **Controls ▸ Rotate Left / Rotate Right**. `mobile_set_orientation` knows only portrait and landscape, not the side, so C2 turns the device from the menus.
  - **The keyboard:** **Device ▸ Keyboard ▸ Simulate Hardware Keyboard** and **Toggle Software Keyboard**.
  - **Xcode 27.1:** a new device starts with Simulate Hardware Keyboard on, and the iPhone's Keyboard menu once offered Toggle Software Keyboard alone, which then shows or hides the on-screen keyboard while a field has the focus.
  - **Xcode 27.0:** the iPad's Keyboard menu offered only Toggle Software Keyboard and Controls no Rotate items, and the iPad switched to its hardware-keyboard mode by itself now and then.
  - **Earlier Xcode versions** have the Simulator app, with **Device ▸ Rotate Left / Rotate Right** and **I/O ▸ Keyboard ▸ Connect Hardware Keyboard** (⇧⌘K) and **Toggle Software Keyboard** (⌘K).
  - **From a script:** reach the menus with `osascript`, after bringing the app to the front, for example `osascript -e 'tell application id "com.apple.dt.Devices" to activate' -e 'tell application "System Events" to tell process "DeviceHub" to click menu item "Landscape Left" of menu "Orientation" of menu item "Orientation" of menu "Device" of menu bar 1'` (with the Simulator app, `process "Simulator"` and `menu item "Rotate Left" of menu "Device"`). Read whether a menu item is on from its `AXMenuItemMarkChar` attribute, ✓ when on. macOS asks the developer once to let the terminal control the computer (Privacy & Security ▸ Accessibility).
  - **When the menus cannot be reached:** DeviceHub may show `osascript` no window at all (`count windows` gave 0 on 2026-10-19, and a window the next day); `mobile_set_orientation` then turns the device. Keys that `osascript` sends to DeviceHub never reached the device, even with **Device ▸ Keyboard ▸ Keyboard Capture** on: send them with mobilecli instead (Typing, below).
- **The clipboard.** DeviceHub copies the Mac's clipboard into the device (**Edit ▸ Use Shared Clipboard**): a paste can bring in whatever the Mac holds, such as a sign-in code. Turn that item off, or set the device's clipboard with `mobile_clipboard` right before each paste, and check what was pasted before saving.
- **Typing and the on-screen keyboard.** Every keyboard check but D6 and K18 needs the on-screen keyboard: turn Simulate Hardware Keyboard off, since a new device has it on, or, when the menu lacks it, use Toggle Software Keyboard once the editor has the focus, and take a screenshot to see which keyboard shows: `defaults write com.apple.iphonesimulator ConnectHardwareKeyboard -bool false` has no effect on DeviceHub. `mobile_type_keys` types as a hardware keyboard does: iOS may hide the on-screen keyboard, it skips iOS's smart punctuation and capitals (so J1 needs the on-screen keys), and it can lose its first character when the field has just been focused. Take a screenshot after typing; if the on-screen keyboard went away, enter text by tapping its keys, or paste it (`mobile_clipboard`, then tap the cursor and **Paste**). The Simulator's double tap and long press do not select a word, and dragging a selection's handle does not move it: D5's and K7's selections are then BLOCKED, and K8 uses a selection the Simulator can make, which the report names. Arrow keys, with or without Shift, as a hardware keyboard sends them: `mobilecli io keys down --device <device>`, or `shift+down` in place of `down`, with the binary in pnpm's dlx cache (above). These, like DeviceHub's menus, can bring the on-screen keyboard back: take a screenshot to see which keyboard shows.
- **Measuring.** Screenshots are in pixels, 3 per point on an iPhone and 2 on an iPad. Measure gaps and overlaps on them with a short script (`uv run --with pillow python …`). When a value from the page is needed, such as `visualViewport` or a box's position, ask the developer to open Safari's **Develop ▸ Simulator** Web Inspector on the Mac and run what you give them.

## Troubleshooting

| What happens                                                                                                                          | What to do                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Every `mobile` tool answers "mobilecli is not available or not working properly"                                                      | mobilecli is not installed hoisted: check `.mcp.json`'s `node-linker=hoisted`, then run its command once with `--config.dlx-cache-max-age=0` (see Install).                                                                                                                                                                                                                                                                                                        |
| A tool fails to start mobilecli's agent on a device                                                                                   | Install the agent on that device: `mobilecli agent install --device <device>`, with the binary in pnpm's dlx cache (`find ~/Library/Caches/pnpm/dlx -type f -name mobilecli-darwin-arm64`). mobilecli needs its agent on each new device.                                                                                                                                                                                                                          |
| "timed out waiting for WebDriverAgent to be ready"                                                                                    | After a device boots, the agent can take a few seconds to answer, and its first start on a new device can time out: the next call starts it.                                                                                                                                                                                                                                                                                                                       |
| `mobile_list_available_devices` lists no simulator, nor does `mobilecli devices`, while `xcrun simctl list devices` shows them booted | mobilecli runs a daemon of its own (`mobilecli-darwin-arm64 daemon start`), which another mobile-mcp install, such as another worktree's or one that `npx` ran, may have started. Stop it (`pgrep -fl mobilecli`, then `kill` its process), and the next tool call starts the right one. If that one still lists none, start it from a terminal with `mobilecli devices`, which lists the simulators, and mobile-mcp then sees them too (both seen on 2026-10-19). |
| `mobile_list_available_devices` lists an iPhone or iPad plugged into the Mac (`"type":"real"`)                                        | Use only the simulators' IDs.                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| A device is gone mid-run                                                                                                              | It shut down, for example when its window closed: `xcrun simctl boot` it, and override its status bar again (see Devices).                                                                                                                                                                                                                                                                                                                                         |
| `osascript` finds no DeviceHub window, or its keys never reach the device                                                             | Turn the device with `mobile_set_orientation`, which cannot pick the side that C2 asks for, and send keys with mobilecli (see Tools).                                                                                                                                                                                                                                                                                                                              |
